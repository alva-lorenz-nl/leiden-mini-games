## 3. 核心玩法与数值系统

### 3.1 三条资源线

```
产出 = herRate() × stabFactor() × catMult() × (1 + 0.05 × frag) × buffMult()
```

- **灵感算力 `S.ip`**：主货币。`S.run` = 本轮累计（用于转生），`S.all` = 历史累计（用于解锁收藏室）。
- **稳定性 `S.stab`**：0–100 的效率系数。
  - `stabFactor() = 0.30 + 0.70 × (stab/100)` → 归零时仍有 30% 产出，不会死锁。
  - 每秒变化：`S.stab += (alvaRate() - heat()) × dt`，钳制在 [0, 100]。
- **记忆碎片 `S.frag`**：转生产出，每片全局 +5%。

### 3.2 三组升级（`HER` / `ALV` / `CAT` 数组）

| 组 | 数量 | 作用 | 涨价系数 `g` |
|---|---|---|---|
| `HER`（赫尔曼） | 8 项 | `val` 累加进 `herRate()`；每级 `heat +1` | 1.12–1.15 |
| `ALV`（阿尔瓦） | 6 项 | `val` 累加进 `alvaRate()`（散热） | 1.14 |
| `CAT`（小猫） | 3 项 | `val` 是**倍率**，按 `Math.pow(val, lv)` 连乘 | 2.40 / 2.60 / 3.00，有 `max` 上限 |

价格公式：`Math.ceil(cost × g^lv)`（见 `priceOf()`）。

**基础值（未购买任何东西时）**：`herRate() = 0.5`，`alvaRate() = 1.0`，`heat() = 0.8 + herRate() × 0.010`。
→ 开局净散热为正，稳定性从 100 起步；买赫尔曼的设备会逐渐把净散热拉向负值，玩家必须在两边之间做取舍。**这是本作的核心张力，改数值时不要破坏它。**

### 3.3 转生（`prestige()`）

```js
gainFrag = Math.floor(Math.sqrt(S.run / 1e6))   // 本轮累计满 1e6 才有第一片
```
重置：`ip / run / stab(=100) / lv / buffs / cd`。
**不重置**：`frag`、`all`、`items`、`scene`、`log`、`born`。

### 3.4 其他系统

- **技能**（`doAbility`）：ab1 立即 20 秒产出（−8 稳定性，CD 12s）；ab2 稳定性 +22（CD 40s）；ab3 20 秒 ×2.5（CD 70s）。
- **随机事件**（`EVENTS`）：约 110–180 秒触发一次，需 `S.run > 5000`。每个事件两个选项，各自调用 `gain / addStab / buff / spend`。这是唯一会弹模态框的地方。
- **收藏室**（`ITEMS`）：按 `S.all` 阈值解锁，每件有 `a`（阿尔瓦视角）和 `h`（赫尔曼视角）两段旁白。
- **场景**（`SCENES`）：0–5 共 6 阶段，由 `HER/ALV/CAT` 里的 `scene` 字段驱动，只升不降。
- **离线收益**（`offline()`）：上限 8 小时，按 50% 效率结算，同时 `stab -= dt × 0.002`。

## 5. 存档格式与兼容性（**最容易踩坑的地方**）

```js
SAVE_KEY = 'leiden_lab_idle_v1'
// localStorage 里存的是 JSON.stringify(S)
```

`S` 的结构：

```js
{
  ip, run, all, stab,           // number
  lv: { h1: 3, a2: 1, ... },    // 设备等级，键为设备 id
  frag, scene,                  // number
  items: ['i1','i2'],           // 收藏 id 数组
  buffs: [{ m, until }],        // until 是绝对毫秒时间戳
  cd: { ab1, ab2, ab3 },        // 剩余冷却秒数
  evtAt, evtOpen,               // 事件时间/开合状态
  log: [{ t, text, cls }],      // 最多 80 条
  born, last                    // 毫秒时间戳
}
```

`load()` 的写法是**逐字段类型校验**（`typeof d[k] === 'number'`、`Array.isArray`），缺失或类型不对的字段会静默保留默认值。这是刻意的容错设计，请保留这个风格。

### 修改存档结构时的强制要求

1. **不要改 `SAVE_KEY`**，除非你同时写好迁移逻辑（读旧 key → 转换 → 写新 key）。
2. **新增字段必须有默认值**，并且 `load()` 里要能容忍旧存档缺这个字段。
3. **删除或重命名设备 id**（`h1`/`a1`/`b1` 等）会让老存档的等级凭空消失。若必须改，在 `load()` 里做 id 映射。
4. 改完请手动测试：**新开局** + **一份旧存档**（可先导出当前存档备份）两种情况都要能正常跑。

## 7. 本次交接希望完善的方向（待办）

按优先级排列，**每条都请先给出方案再动手**：

1. **数值曲线体检**
   - 目前 `HER` 与 `ALV` 的成本/产出比是手工拍的，中后期（h5 之后）可能出现"要么卡死、要么暴富"的断层。
   - 建议写一个独立的离线模拟脚本（Python 或 Node 都行，**放在仓库外或 docs/ 下，不要塞进 HTML**），模拟"贪心购买最便宜项"策略下的通关时间曲线，检查：首次转生耗时、第二次转生的边际收益、场景 3–5 的解锁节奏是否拖沓。
   - 目标是：**首次转生 20–40 分钟，之后每次转生间隔逐次缩短但收益递增**。
2. **稳定性系统的手感**
   - 目前稳定性只影响产出系数，惩罚偏"软"。可考虑让 `stab < 20` 时触发视觉/音效层面的紧张感（闪烁、噪声），但**不要加硬性失败惩罚**（本作定位是放松向，不能出现"游戏崩了"）。
3. **离线收益上限与提示**
   - 8 小时上限 + 50% 效率目前是硬编码。若改，请在界面上明确告知玩家。
4. **移动端适配**
   - 当前布局在窄屏上偏挤，商店行和技能按钮容易换行错位。改动时只动 CSS。
5. **无障碍与性能**
   - `renderShop()` 只在切换分组/购买时重建 DOM（已优化），但 `updateShop()` 每 0.1 秒会把每一行的 `desc` 重新 `innerHTML` 一遍（见 1013–1029 行）。低端设备上可改为只在 `lv` 变化时更新描述，平时仅更新价格与 `disabled`。
